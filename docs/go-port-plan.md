# Go-порт для fxTunnel

Основа: `grandvan709/yookassa-to-mynalog`, commit
`f9f72fdad6e6cac242a52f50c1cdb93b71d24daa`, Apache-2.0.
Форк: `mephistofox/yookassa-to-mynalog`, ветка `feat/go-fxtunnel`.

## Цель и границы

Отдельный Go-сервис выдаёт чеки НПД по успешным рублёвым платежам fxTunnel
в ЮKassa и доставляет ссылки покупателям по SMTP. Вход в ФНС через refresh
token + исходный device ID, без пароля Госуслуг. Платёжный поток fxTunnel
и выдача подписок не зависят от доступности сервиса чеков.

Это функциональный порт ядра, а не обещание полной совместимости с Python:
Telegram-админка, Telegram-доставка, автообновление, cron-синтаксис,
SOCKS-прокси и миграция Python-state не входят в эту версию. Исходный Python
сохранён. Go использует отдельную БД. Нельзя запускать два сервиса выдачи
чеков на один и тот же диапазон платежей.

## Проверенное сопряжение с fxTunnel

`internal/server/payment/yookassa.go:CreateCheckoutSession` и
`internal/server/scheduler/scheduler.go:createAutopayment` передают
`metadata.email`, `user_id`, `subscription_id`, `plan_id`, `invoice_id`.
Порт читает `metadata.email` из авторизованного ответа API ЮKassa,
а не из входящего публичного запроса. Контакты из metadata не включаются
в описание дохода ФНС или логи. Клиенты этой версии — физические лица.
Creem и иностранная валюта в НПД автоматически не включаются.

## Этапы реализации

1. **Основа и состояние.** Go module, точные суммы в копейках, проверка env,
   SQLite WAL/FULL, версия схемы, локальная межпроцессная блокировка,
   транзакционная фиксация чеков и outbox. Ключи и БД недоступны другим
   пользователям; резервное копирование — через SQLite online backup/VACUUM INTO.
2. **Клиенты API.** ЮKassa: Basic auth, все страницы, отдельные checkpoint
   платежей и возвратов. Платежи выбираются по времени подтверждения,
   а не создания, чтобы поздняя оплата не потерялась. ФНС: refresh/password,
   сохранение ротации refresh token до использования нового access token,
   одно повторное обновление при 401, ограниченные ответы и таймауты.
   HTTP-ошибки журналируются кодом, без тела ответа и секретов.
3. **Выдача.** Сканер сохраняет все полученные страницы в SQLite до продвижения
   checkpoint. Небольшое перекрытие окон + UNIQUE payment ID. Перед POST
   записывается фаза `creating`. Потеря ответа/5xx/невалидный 2xx переводят
   операцию в сверку, а не в повторный POST. Поиск учитывает точную метку
   платежа, сумму, дату и аннулирование. Отсутствие в списке не доказывает,
   что POST не был выполнен: неизвестные операции повторно не создаются.
4. **Доставка.** Отдельный постоянный outbox, TLS SMTP, UTF-8, стабильный
   Message-ID, проверка адреса. Ошибка доставки не создаёт новый чек.
   Доставка имеет гарантию at-least-once: потеря SMTP ACK может дать повторное
   письмо. Без SMTP чеки видны в состоянии, доставка отмечена как заблокированная.
5. **Возвраты.** По умолчанию выключены. Подтверждённый полный возврат
   аннулирует чек; частичный — аннулирует старый и создаёт чек на остаток с
   исходной датой дохода. Каждый переход сохраняется до сетевого запроса.
   Возвраты одного платежа обрабатываются последовательно. Pending-возвраты
   сохраняются и перепроверяются по ID, чтобы переход в succeeded не потерялся
   за checkpoint. Нет исходного локального чека — ручная сверка, без создания
   исторического дохода задним числом по предположению.
6. **Эксплуатация.** `serve`, `once`, `status`, read-only `check`, `backup`,
   loopback health/readiness, Docker Compose с non-root пользователем,
   отдельный volume, пошаговое включение. Блокировки/очереди видны через status
   и readiness. Отключение сервиса чеков не меняет приём платежей.
7. **Проверки.** HTTP-контрактные тесты, точные деньги, повреждённые/повторные
   страницы, позднее подтверждение, рестарт между POST и commit, ротация токена,
   401, 429, 5xx, таймаут, частичные/полные/последовательные возвраты,
   outbox и безопасный повтор. `go test -race ./...`, `go vet ./...`, сборка.

## Решения для защиты от дублей

- Нет распределённой транзакции между ФНС и SQLite; нельзя честно гарантировать
  exactly-once только локальным UNIQUE. Неопределённость всегда видна оператору.
- Для неизвестного результата выполняются только GET-сверки. Автоматический
  новый POST допускается лишь после явно отклонённого запроса (например 429)
  или до фактической попытки записи (ошибка авторизации).
- После аварийного рестарта фазы `creating`/`cancelling` считаются неизвестными.
- Порт не получает прав изменять платежи ЮKassa: используются только GET.
- Внешние URL API фиксированы в production-конфигурации. Тесты подменяют
  transport/конструкторы, а не открывают настраиваемый прокси к секретам.

## План включения

1. Выбрать точную границу `SYNC_START_DATE` после последнего вручную выданного
   чека. На копии/тестовом магазине выполнить `check`: он ничего не пишет в ФНС.
2. Пользователь локально помещает токен, device ID, ИНН, ключ ЮKassa и SMTP
   в защищённый env/secret. Секреты не передаются в GitHub и сообщения.
3. `check` проверяет только чтение API и авторизацию; успешный тест на моках
   не заменяет проверку реальной сессии ФНС.
4. Одна контролируемая настоящая оплата, проверка дохода в «Моём налоге»,
   суммы до комиссии, даты, ссылки, доставки и повторного `once` без дубля.
5. Включить `serve`, наблюдать очередь и readiness. Возвраты включить отдельно
   после проверки на контролируемом сценарии.

Не делать автоматически: выдачу чеков по всей истории, реальный платёж,
боевую регистрацию/аннулирование доходов, развёртывание на production.
Текущая задача разрешает форк, разработку и публикацию кода в форке.

## Итог реализации

Этапы 1–7 реализованы. Код Go расположен в `cmd/receipts` и
`internal/receipts`. Для разблокирования неопределённых операций добавлены
локальные `retry-payment` и `retry-refund` с явным подтверждением ручной сверки,
для доставки — `set-email`. `status` показывает проблемные ID без email/токенов.

Выполнены `go test -race ./...`, `go vet ./...`, сборка бинарника,
проверка Compose, сборка образа и smoke контейнера без внешней сети.
Подробности: [validation.md](validation.md).

Осталось эксплуатационное включение из предыдущего раздела: выбрать границу,
добавить секреты локально, проверить реальную авторизацию и одну оплату.
Это не выполнялось в рамках разработки. Файлы существующего fxTunnel не менялись.
