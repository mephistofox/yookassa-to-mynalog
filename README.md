# ЮKassa → «Мой налог»: Go-порт для fxTunnel

**Встроенный режим:** публичная библиотека [`pkg/receipts`](pkg/receipts) работает
внутри fxTunnel, с его PostgreSQL и SMTP. Отдельный процесс и контейнер не нужны.
Контракт хранения — [`pkg/state`](pkg/state); [инструкция встраивания](docs/embedding.md).
Описанный ниже CLI с SQLite и Docker — необязательный standalone-вариант.

Отдельный сервис регистрирует доходы НПД по оплатам fxTunnel в ЮKassa,
получает чеки ФНС и отправляет ссылки покупателям на email. Поддерживает
первые платежи и продления, вход через Госуслуги **без пароля**, постоянную
очередь, восстановление после сбоев и возвраты.

Форк [grandvan709/yookassa-to-mynalog](https://github.com/grandvan709/yookassa-to-mynalog),
Apache-2.0. Go-порт меняет runtime и модель состояния; это не замена Python
без настройки. Исходники Python сохранены, описание — [README.python.md](README.python.md).

## Как это работает

```text
ЮKassa (GET API) → сканер → SQLite → очередь ФНС → чек → SMTP outbox → покупатель
                                           ↕
                                   сверка после сбоя
```

- Сканирование по времени **подтверждения оплаты** (`captured_at`), с полной
  пагинацией, сохранением checkpoint и перекрытием окон. Поздняя оплата старого
  заказа попадёт в обработку.
- Деньги хранятся в копейках; в ФНС передаётся полная сумма оплаты до комиссии.
- Перед каждой записью ФНС сохраняется фаза операции. Потерянный ответ, 5xx
  или аварийный рестарт требуют GET-сверки. Отсутствие чека в одном ответе
  ФНС не разрешает автоматический повтор POST.
- Ротация refresh token сохраняется в SQLite и переживает рестарт.
- Письма имеют отдельную очередь: сбой SMTP не создаёт повторный чек.
  Гарантия доставки — **at-least-once**: потеря SMTP-подтверждения может дать
  повторное письмо. Стабильный Message-ID помогает почтовым системам распознать его.
- Полный возврат аннулирует чек, частичный заменяет его чеком на остаток с
  исходной датой дохода. Возвраты одного платежа обрабатываются последовательно;
  pending-возвраты продолжают отслеживаться после продвижения checkpoint.
- `/healthz` проверяет процесс, `/readyz` — свежесть работы и проблемные очереди.

## Сопряжение с fxTunnel

Нужен отдельный магазин ЮKassa для fxTunnel. Первые оплаты и автопродления
уже передают `metadata.email`, `invoice_id`, `user_id`, `subscription_id`,
`plan_id`. Email берётся из авторизованного ответа ЮKassa. При отсутствии
служебных ключей платёж блокируется для сверки; при отсутствии email чек
создаётся, а доставка ждёт уточнения адреса.

Менять обработчик платежей или вебхуки fxTunnel не требуется. Сервис чеков
не участвует в выдаче подписок и не имеет кода изменения платежей ЮKassa.
Неработающая ФНС не блокирует оплату пользователем.

Версия рассчитана на клиентов-физлиц и рублёвые платежи ЮKassa. Тестовые
платежи игнорируются, другие валюты и неподходящие метаданные блокируются.
Creem не обрабатывается. В payload ФНС сохранён формат upstream, включая
`paymentType=CASH`; он не означает приём наличных на стороне ЮKassa.

## Первый запуск

1. Сверьте уже выданные вручную чеки и выберите точный момент начала.
   `SYNC_START_DATE` обязателен, например `2026-10-17T18:00:00+03:00`.
   Это дата подтверждения платежа, не дата создания заказа. Старые платежи
   вне диапазона не будут учтены этим сервисом.
2. Скопируйте `.env.example` в `.env`, установите права `600`, заполните
   магазин/ключ ЮKassa, ИНН, refresh token, device ID и SMTP.
3. Соберите образ и выполните проверку чтения:

   ```sh
   docker compose build
   docker compose run --rm receipts check
   ```

   `check` проверяет авторизацию ФНС и чтение ЮKassa. Он не создаёт/аннулирует
   доходы и не отправляет письма, но может сохранить обновлённый токен локально.
4. После сверки границы выполните одну контролируемую оплату и один цикл:

   ```sh
   docker compose run --rm receipts once
   docker compose run --rm receipts status
   ```

   Проверьте чек в «Моём налоге», сумму, дату и письмо. Повторный `once`
   должен увидеть прежний payment ID и не создать новый доход.
5. Запустите постоянный сервис:

   ```sh
   docker compose up -d
   docker compose logs --tail=100 receipts
   curl -fsS http://127.0.0.1:8099/readyz
   ```

`once` и `serve` делают реальные записи в ФНС. В этом репозитории нет ваших
ключей, выбранной границы и результатов проверки настоящего аккаунта.
Возвраты по умолчанию выключены; включайте `REFUNDS_ENABLED=true` отдельно
после проверки контролируемого сценария.

## Авторизация без пароля

Войдите на `https://lknpd.nalog.ru` через Госуслуги. В Network браузера
найдите ответ `auth/esia` или `auth/token`. Поместите `refreshToken` в
`MOY_NALOG_REFRESH_TOKEN`, исходный `deviceInfo.sourceDeviceId` — в `DEVICE_ID`.
Укажите свой ИНН в `MOY_NALOG_RECEIPT_INN`. Пароль Госуслуг сервису не нужен.

Токен даёт доступ к кабинету. Храните `.env`, БД и резервные копии как секреты.
Все переменные поддерживают `NAME_FILE=/run/secrets/...`; нельзя одновременно
задать `NAME` и `NAME_FILE`. API ФНС неофициальный, его изменения могут
потребовать обновления интеграции или повторного входа.

При ротации сервис использует сохранённый токен, пока исходный токен и device
ID в конфигурации прежние. Замена исходного токена в env явно переинициализирует
авторизацию. Истёкший/отозванный токен требуется заменить вручную. Запросы
ФНС разделены интервалом `FNS_REQUEST_INTERVAL` (по умолчанию 1 секунда).

## Команды и восстановление

```sh
receipts serve                       # постоянный сканер и очередь
receipts once                        # сканирование + обработка одного цикла
receipts check                       # только чтение внешних данных и авторизация
receipts status --db /data/receipts-go.db
receipts backup --db /data/receipts-go.db --out /data/backup-20261017.db
receipts set-email --payment PAYMENT_ID --email customer@example.com
receipts retry-payment --payment PAYMENT_ID --confirmed-absent
receipts retry-refund --refund REFUND_ID --confirmed-state
```

`status` не требует ключей API; выводит checkpoint, счётчики и проблемные ID
без email и токенов. `backup` делает согласованный SQLite-снимок вместе с WAL;
имя назначения должно быть новым. Защитите и регулярно копируйте backup за
пределы контейнера. Не копируйте только живой `.db` без WAL.

Операционные команды с записью используют ту же блокировку, что и worker:
перед `set-email` или `retry-*` остановите `serve`; после команды запустите его.
При восстановлении backup остановите все процессы, сохраните текущие `.db`,
`-wal`, `-shm`, замените их согласованным снимком и запустите один writer.

Фазы `uncertain`, `creating`, `cancelling`, `replacing` видны в `/readyz` и
`status`. Сервис продолжает GET-сверку без повторного финансового POST.
Если чек долго не находится, **сначала проверьте кабинет «Мой налог» вручную**.
Только затем используйте `retry-payment --confirmed-absent`. Команда сначала
ещё раз ищет точный чек; если он найден, привяжет его, иначе разрешит одну
новую попытку очереди. Аналогично `retry-refund --confirmed-state` требует
ручной проверки аннулирования и замены, сверяет состояние и подготавливает
продолжение. Неправильное подтверждение оператором может создать дубль.

`blocked` означает ошибку данных или явное отклонение ФНС. Неподдерживаемую
валюту и отсутствие метаданных нельзя обойти командой повтора. Исторические
возвраты без локального исходного чека требуют отдельной ручной сверки.
`DELIVERY_MODE=disabled` оставляет письма в очереди и даёт non-ready при наличии
недоставленных чеков. Ошибки SMTP и временные сбои ФНС повторяются с backoff.

## Настройки

Основные значения и пустые поля перечислены в [.env.example](.env.example).
`POLL_INTERVAL=1m`, `RETRY_INTERVAL=15s`, `REQUEST_TIMEOUT=30s`,
`HEALTH_MAX_AGE=15m`. Один цикл ограничен двумя минутами; незавершённая
работа остаётся в SQLite. `INCOME_DESCRIPTION` задаёт текст услуги без личных
данных; к нему добавляется уникальная метка payment ID.

SMTP требует STARTTLS (`SMTP_TLS=starttls`, обычно порт 587) или TLS
(`SMTP_TLS=tls`, обычно 465), проверку сертификата отключить нельзя.
`YOOKASSA_SOURCE_IP` и `NALOG_SOURCE_IP` позволяют привязать исходящие запросы
к локальному IP. В Docker bridge нельзя указывать IP хоста как локальный адрес
контейнера: для такого сценария настройте egress/NAT или отдельный network mode.

Бинарник без Compose не читает `.env` автоматически: передайте переменные через
окружение менеджера сервиса. Compose держит health-порт на loopback хоста,
контейнер работает от non-root пользователя с read-only rootfs.

## Сборка и проверки

Нужны Go 1.26; C compiler требуется только необязательному SQLite-адаптеру.
Для standalone в production используется Linux
(`flock`); macOS поддерживает ту же блокировку. Windows этой версией не поддерживается.

```sh
go test -race ./...
go vet ./...
go build -trimpath -o bin/receipts ./cmd/receipts
```

Тесты используют локальные HTTP-серверы и временные SQLite-базы. Они покрывают
контракты API, ротацию токена, точные суммы, пагинацию, позднюю оплату, потерянные
ответы и рестарт, возвраты, очереди писем, блокировку writer и backup.
Настоящие ФНС, ЮKassa и SMTP в автоматических тестах не используются.

## Отличия от Python и границы переноса

Python-админбот Telegram, Telegram-доставка, автообновление, SOCKS-прокси,
cron-синтаксис и импорт Python-state в Go не перенесены. Состояние Go отдельное;
использование БД Python отвергается. Обработка Telegram здесь не нужна fxTunnel,
который передаёт email в metadata.

Не запускайте Python и Go для одного диапазона платежей: их локальная
дедупликация не общая. Изменение описания услуги и потеря/откат SQLite требуют
сверки с ФНС. История автоматически не удаляется. Полный план и сценарий
включения: [docs/go-port-plan.md](docs/go-port-plan.md).
